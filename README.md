# 工作台提示词助手

[![GitHub license](https://img.shields.io/github/license/wangchentalk/workbench-prompt-assistant)](https://github.com/wangchentalk/workbench-prompt-assistant/blob/main/LICENSE)
[![GitHub stars](https://img.shields.io/github/stars/wangchentalk/workbench-prompt-assistant)](https://github.com/wangchentalk/workbench-prompt-assistant/stargazers)
[![GitHub release](https://img.shields.io/github/v/release/wangchentalk/workbench-prompt-assistant?include_prereleases)](https://github.com/wangchentalk/workbench-prompt-assistant/releases)

> 把模糊的工作台想法，整理成可交给工作台搭建师的完整提示词。

工作台提示词助手面向没有产品设计和开发经验的用户。用户只需从一句话开始，助手就会通过低门槛、多轮、动态的需求访谈，逐步澄清目标、用户、场景、功能、页面、流程、数据、权限、异常和验收标准，最后输出一份可直接复制使用的工作台搭建提示词。

项目采用中文优先的表达方式，适合个人、小团队和业务人员整理工作台需求。

## 核心能力

| 能力 | 解决的问题 | 使用方式 |
| --- | --- | --- |
| 模糊想法澄清 | 不知道如何描述工作台 | 从一句自然语言开始，逐步确认目标和使用场景 |
| 动态需求访谈 | 不清楚下一步该回答什么 | 根据前文给出针对性问题和推荐方向 |
| 结构化选项 | 选择过多，难以比较 | 优先使用宿主环境提供的单选或多选组件 |
| 文字选项兜底 | 当前环境缺少选择组件 | 回复序号或直接补充自己的方案 |
| 需求台账 | 已确认内容和猜测混在一起 | 持续区分确认项、建议值、待确认项和风险 |
| MVP 范围控制 | 功能愿望过多，首版难以落地 | 将需求划分为核心闭环、效率增强、后续扩展和暂缓内容 |
| 业务结构建模 | 页面、流程和数据彼此脱节 | 同步梳理页面、状态、数据对象、权限和异常处理 |
| 场景模拟验收 | 方案看起来完整，实际无法使用 | 用典型场景检查从开始到结束的业务闭环 |
| 二次优化 | 初次搭建后发现问题 | 根据搭建结果生成针对页面、流程或交互的修订提示词 |

## 三步上手

### 第一步  安装 Skill

选择一种安装方式，将项目放入用户级 Skill 目录。

#### 方式一  使用 Git 克隆

适合需要持续更新项目的用户。

```bash
git clone https://github.com/wangchentalk/workbench-prompt-assistant.git ~/.workbuddy/skills/workbench-prompt-assistant
```

Windows 用户可以在 PowerShell 中执行：

```powershell
git clone https://github.com/wangchentalk/workbench-prompt-assistant.git "$env:USERPROFILE\.workbuddy\skills\workbench-prompt-assistant"
```

#### 方式二  下载 ZIP 压缩包

1. 打开本项目的 GitHub 页面。
2. 点击 `Code`。
3. 选择 `Download ZIP`。
4. 解压下载的压缩包。
5. 将 `workbench-prompt-assistant` 文件夹复制到用户级 Skill 目录。
6. 确认该文件夹内直接包含 `SKILL.md`、`README.md`、`references` 和 `tests`。

用户级 Skill 目录通常为：

```text
Windows
%USERPROFILE%\.workbuddy\skills\workbench-prompt-assistant\

macOS 或 Linux
~/.workbuddy/skills/workbench-prompt-assistant/
```

安装完成后，刷新 Skill 列表或重新启动 WorkBuddy。

### 第二步  说出你的想法

可以只输入一句话：

```text
我想做一个工作台。
```

也可以直接补充业务背景：

```text
我想做一个客户管理工作台，给销售团队使用，解决客户资料分散和跟进不及时的问题。
```

助手会根据你的回答继续提问。你无需提前掌握产品设计、数据库、接口或权限知识。

当你暂时无法判断时，可以回复：

```text
请你推荐
```

或：

```text
我不确定，按常见做法设计。
```

助手会给出建议值，并在最终结果中标出需要后续确认的内容。

### 第三步  拿到可执行方案

完成必要的需求确认后，助手会输出两部分内容：

1. 工作台制作方案，方便你检查需求是否符合预期。
2. 可直接复制给工作台搭建师的完整搭建提示词。

如果已经完成初次搭建，也可以继续提供截图、页面问题或使用反馈，让助手生成第二版优化提示词。

## 典型触发方式

### 从一句话开始

```text
我想制作一个任务协作工作台，请先通过提问帮我整理需求。
```

### 让助手提供推荐

```text
我想做一个适合小团队使用的运营工作台，具体功能还不确定，请给我几个方向。
```

### 处理功能过多的想法

```text
我希望工作台包含客户管理、审批、数据看板、内容发布、知识库和自动提醒。请帮我划分首版范围。
```

### 明确偏好后继续细化

```text
核心用户是销售主管和销售，首版先做客户跟进、任务提醒和团队看板。请继续设计页面、流程和权限。
```

### 优化已经搭建的工作台

```text
这是当前工作台的问题：销售看不到今天需要跟进的客户，主管也无法查看团队进度。请生成第二版优化提示词。
```

## 四种常用工作模式

### 模式一  模糊想法转工作台目标

适合只有一个初步念头的情况。助手会先确认工作台服务的对象、需要解决的问题和最重要的使用场景，再把想法收敛成一句清晰定位。

### 模式二  业务需求转页面和流程

适合已经知道业务目标，但说不清页面结构的情况。助手会围绕任务顺序梳理页面、模块、状态、操作入口、反馈信息和异常分支。

### 模式三  功能愿望转首版范围

适合功能很多，暂时无法判断优先级的情况。助手会比较业务价值、使用频率、依赖条件和实现成本，帮助你确定核心闭环，并保留后续扩展清单。

### 模式四  搭建结果转第二版优化

适合工作台已经搭建完成，使用过程中出现问题的情况。助手会把问题定位到目标、页面、流程、数据、权限、视觉或外部依赖，再生成可执行的修改提示词。

## 一个完整的使用示例

### 用户输入

```text
我想做一个客户管理工作台，给销售团队使用。现在客户资料分散在表格和聊天记录里，销售经常忘记跟进。请先帮我整理需求，不确定的地方给我推荐。
```

### 助手会重点确认

```text
1. 首版最重要的任务是客户建档、跟进提醒，还是团队业绩查看？
2. 销售和销售主管分别需要查看、创建、编辑哪些内容？
3. 客户跟进是否需要阶段状态，例如待联系、沟通中、已报价和已成交？
4. 是否需要导入现有表格？如果需要，表格中的哪些字段必须保留？
5. 你希望首版优先解决个人跟进效率，还是团队协作和管理？
```

### 可能形成的方案摘要

```text
工作台定位
帮助销售记录客户信息、安排下一步跟进，并帮助主管查看团队跟进进度。

首版核心闭环
客户建档 → 分配负责人 → 记录沟通 → 设置下次跟进 → 查看逾期任务。

主要页面
工作台首页、客户列表、客户详情、跟进任务、团队看板、基础设置。

待确认事项
是否接入外部通讯工具，是否允许销售查看其他成员的客户，是否需要导入历史客户数据。
```

### 最终输出

最终提示词会进一步补齐数据字段、状态变化、角色权限、异常场景、空状态、验收标准和实现边界，供工作台搭建师继续搭建。

## 交互组件说明

选择类问题优先使用宿主环境提供的结构化提问能力。结构化问题至少包含问题内容、简短标题、选项和单选或多选设置。

当宿主环境缺少结构化提问能力，或结构化调用失败时，助手会改用清晰的文字选项。用户可以回复序号，也可以用自然语言表达自己的选择。

项目不会虚构已经显示的弹窗、按钮或选择卡片，也不会把尚未确认的外部连接、账号权限和数据能力写成确定结果。

## 最终方案包含什么

一份完整的工作台搭建方案通常包含以下内容：

- 一句话定位
- 目标用户和使用场景
- 已确认需求与建议值
- 首版核心闭环
- 后续扩展清单
- 页面与模块结构
- 业务流程和状态变化
- 数据对象、字段和关系
- 角色、权限与协作规则
- 异常、空状态和边界场景
- 外部依赖与实现边界
- 视觉和交互方向
- 典型场景模拟
- 可执行的验收标准
- 待确认事项与高风险点
- 可直接复制的完整搭建提示词

## 设计边界

- 负责需求分析、方案整理和提示词生成，不直接完成工作台搭建。
- 保持通用平台视角，用户明确指定平台后再纳入平台约束。
- 不虚构接口、账号、权限、数据源或连接状态。
- 低优先级内容可以采用建议值，同时在输出中单独标记。
- 影响整体架构的内容需要保留在待确认事项中。
- 涉及敏感数据时，需要明确数据范围、访问权限、操作日志和恢复机制。

## 测试

测试用例位于 `tests/test-cases.md`，覆盖以下场景：

- 一句话模糊输入
- 结构化提问优先
- 结构化提问不可用时的文字兜底
- 用户请求推荐
- 暂时跳过专业问题
- 功能过多与首版范围取舍
- 前后回答冲突
- 外部系统依赖不明确
- 数据对象关系缺失
- 立即生成和二次优化
- 平台能力边界

修改核心规则后，建议同步更新参考文档和测试用例。
