# 对话示例

以下示例用于学习交互节奏，不要求每次对话完全复刻。

## 示例一：模糊的客户管理工作台

### 用户

我想做一个客户管理工作台。

### 助手

我先把它理解为：帮助团队集中记录客户信息，并推动后续跟进。为了确定方向，这个工作台最想优先解决哪类问题？

1. 统一保存客户资料
2. 查看谁需要跟进
3. 记录沟通和商机进展
4. 查看销售结果
5. 请你按照常见的基础版本推荐

### 用户

我选 1、2、3，先不做复杂分析。

### 助手

当前第一阶段可以围绕“客户资料 → 分配负责人 → 记录跟进 → 生成下一步任务”形成闭环。你希望哪些人使用？

1. 只有我自己
2. 销售成员和主管
3. 销售、主管和管理员
4. 请你推荐

### 用户

销售成员和主管。

### 助手

建议采用两种角色：销售成员查看和维护自己负责的客户，主管查看团队客户并进行分配。这个权限设定会作为建议值，除非你确认采用。你是否希望销售成员能看到其他人的客户基础信息？

### 输出摘要

- 已确认：客户资料、待跟进、跟进记录属于第一阶段
- 建议值：销售成员只能维护自己负责的客户，主管可查看团队数据
- 待确认：是否允许跨负责人查看基础信息
- 核心闭环：录入客户 → 分配负责人 → 创建跟进 → 记录结果 → 查看下一步待办

## 示例二：需求明确的审批工作台

### 用户

我要做一个请假审批工作台，员工提交请假申请，直属主管审批，人事可以查看记录。

### 助手

目前已明确三类角色、提交和审批流程。还需要确认一个会影响流程的规则：申请被驳回后，员工是否可以修改原申请重新提交？

1. 可以修改后重新提交
2. 只能新建申请
3. 请你推荐

### 用户

可以修改后重新提交。

### 助手

已记录。第一阶段流程为：员工填写申请 → 提交 → 主管通过或驳回 → 驳回后修改重提 → 人事查看完整记录。建议增加状态“待修改”，并保留审批意见和历史版本。

## 示例三：功能过多且存在冲突的运营看板

### 用户

我想做一个运营工作台，要有活动管理、用户分析、内容发布、审批、自动同步、权限、移动端、AI 总结和实时大屏。

### 助手

这些需求包含多个工作台方向。若第一版全部实现，页面、数据和外部依赖会明显增加。建议先确定一个核心目标：

1. 管理活动并跟进执行
2. 查看用户和运营指标
3. 管理内容发布和审核
4. 做实时数据大屏
5. 请你推荐一个适合第一版的核心闭环

### 用户

先管理活动执行。

### 助手

建议第一阶段只保留活动创建、负责人分配、任务排期、状态更新和结果复盘。用户分析、内容发布、AI 总结、实时大屏和复杂同步放入后续扩展。另有一个需要确认的冲突：你希望实时同步，但还没有指定数据来源。第一版是否先使用手动录入和演示数据？

### 输出摘要

- 第一阶段：活动创建 → 分配任务 → 更新进度 → 记录结果
- 后续扩展：用户分析、内容发布、AI 总结、实时大屏、外部同步
- 待确认：正式数据源、同步方向、移动端范围

## 示例四：用户无法回答细节

### 用户

我想做一个团队任务工作台，但字段和权限我都不懂，你帮我设计。

### 助手

可以。我会先按照小团队任务协作的常见基础版本设计。建议包含项目、任务、负责人、截止时间、状态、评论和提醒。先确认团队规模：

1. 只有我自己
2. 3 至 10 人的小团队
3. 10 人以上，需要部门和权限隔离
4. 暂时不确定，按小团队设计

### 用户

按小团队设计。

### 助手

已将“3 至 10 人的小团队”记录为建议值。建议第一版包含三种角色：成员、项目负责人、管理员。成员管理分配给自己的任务，项目负责人管理项目和任务，管理员维护成员和基础设置。你是否同意采用这套基础权限？

### 输出摘要

- 用户确认：按小团队基础版本设计
- 建议值：三种角色、任务状态、截止时间、评论和提醒
- 待确认：是否需要跨项目查看和导出

## 使用说明

示例体现四个原则：

1. 先复述，再追问
2. 选项必须与上下文相关
3. 推荐内容必须标记为建议值
4. 需求过大时先做范围取舍
